# Semantic decisions

Kept up to date with the implementation (spec §5, §11). Each entry notes the milestone that introduced it.

## M0: model and validation

- **Qualified ids.** Every element is identified by `<file name>#<element id>` (`QId`). Ids are only unique inside one file.
- **Process ids are global.** Loading a second file that defines an already known process id fails with an error naming both files.
- **Namespace matching.** BPMN elements are matched by namespace URI, so `bpmn:`, `bpmn2:` and unprefixed documents all work. Only `zeebe:calledElement@processId` and `zeebe:calledDecision@decisionId` are read from vendor extensions; everything else is ignored.
- **Ignored elements.** Data objects, data stores, associations, annotations and groups are not flow nodes and are skipped silently.
- **Unsupported elements.** `complexGateway`, `transaction`, `adHocSubProcess` and unknown event definitions (e.g. conditional, compensation) are kept in the model as `Unsupported` and reported as warnings.
- **Lanes.** A node's lane is the innermost lane that lists it in `flowNodeRef`.
- **Dangling references** in sequence flows, boundary events (`attachedToRef`) and message flows are parse errors naming the file and element.
- **Reachability** (for "intermediate catch event can never be reached") starts from all start events, follows sequence flows and link throw → link catch jumps, and treats boundary events as reachable once their activity is. Message and signal arrival do not make an intermediate catch event reachable; it needs an incoming flow.
- **Exempt from the "no outgoing flow" check:** end events and link throw events.
- **Deferred.** BPMNDI shapes/edges (diagram view, M6) and scenario-dependent checks (gateway probabilities, M1) are not parsed yet. Discovery of referenced files from a single main file (M4) is not implemented; `Project::add_dir` loads every `*.bpmn` in a folder.

## M1: engine, scenario and statistics

- **Event order.** The queue is ordered by `(time, sequence number)`; the sequence number is the scheduling order, so events at the same time run in a fixed order. All maps are `BTreeMap`s. One `ChaCha8Rng` per replication; replication `i` uses `seed + i`.
- **First arrival at t = 0.** Every arrival generator fires its first case at time 0, then after each sampled inter-arrival time.
- **Case count.** `simulation.cases` is the total number of cases started across all generators and is required (`horizon` arrives with M5). The generator firing *after* the last case starts nothing; it only advances the clock. It therefore marks the end of the observation window, which makes V1's utilisation exactly 1/6.
- **Observation window** = time of the last event processed (last completion or that final generator firing, whichever is later). Utilisation = busy time ÷ (count × window). Resource statistics include warm-up cases; only case and activity statistics exclude them.
- **Warm-up.** The first `warm_up_cases` cases *to complete* are excluded from case and activity statistics. Cases that never complete are never counted in cycle-time statistics.
- **Triggers.** One process instance is created per distinct process among the triggers of an arrival; each trigger gets a token. A case completes when all its instances have no tokens left.
- **Tasks.** Waiting = start − arrival at the task; processing = sampled duration. The duration is sampled when the task starts. A resource freed by a finishing task goes to the head of its FIFO queue before the finished token moves on.
- **Resources.** Pool = `resource` override, else lane name, else participant name; a task with none of these needs no resource (unlimited). A named pool missing under `[resources]` is a scenario error. Every task of an instantiated process needs an `[activities]` entry with a duration.
- **Costs.** Activity cost = processing time × pool `cost_per_hour` ÷ 3600 + `fixed_cost`; case cost is the sum. Pool cost = busy time × rate.
- **XOR split.** Every outgoing flow needs a probability, and they must sum to 1 (±1e-9); the `default` flow gets no special treatment yet. Probability keys are flow ids local to the gateway's file, or qualified (`file#flow`). Single-outgoing XOR gateways need no entry; XOR joins pass every token.
- **AND join.** Tokens wait per instance and per incoming flow; the join fires when every incoming flow has a token and consumes one from each, so tokens of different instances can never mix. A node with several outgoing flows (task, event, gateway) sends a token down each of them, except XOR.
- **Implicit end.** A token leaving a non-end node with no outgoing flow is consumed silently (validation warns).
- **Stuck report.** Tokens alive when the queue runs empty are listed with case, process, element and state (`working`, `queued for resource 'X'`, `waiting at AND join`).
- **Percentiles** use linear interpolation between closest ranks (R type 7); standard deviation is the sample standard deviation.
- **Scenario strictness.** Unknown keys are errors (typos). Sections of later milestones (`calendars`, `events`, `boundary`, `messages`, `horizon`, resource `calendar`, `model.files`) are accepted and reported as ignored warnings. Elements the engine cannot run yet (messages, timers, subprocesses, call activities, boundary events, OR/event gateways, non-none end events) make binding fail instead of being silently skipped.

## M2: GUI and export

- **Theme.** The top bar switches between System, Light and Dark (egui's built-in themes); the choice is stored with the window state (eframe persistence) and used at the next start. All colours of the GUI and the diagram come from the theme, except the case colours of tokens, the heat map and the replay badges, which read on both.
- **GUI scope.** `sim-gui` only calls `sim-core` (bind, run, export) and displays results. A run executes on a worker thread; the scenario is bound on that thread and bind errors come back as a message. Progress is per finished replication.
- **Opening files.** Opening one file loads only that file (automatic discovery of referenced files comes with M4); opening a folder loads every `*.bpmn` in it. Opening a model while the scenario is still empty generates a skeleton; with a scenario already there, it is updated from the model (see "Configuring in the desktop app").
- **Skeleton.** One `[activities]` entry per task (10 min fixed), one `[gateways]` entry per XOR split (equal probabilities), one resource pool (count 1) per lane / pool name used by a task, and one arrival every hour triggering all none/timer start events of the main file (default: first file). Keys are qualified ids. A decision input read by several decisions is written once (under the first decision), so a fresh skeleton binds without warnings.
- **Scenario files** are written back with durations in the largest exact unit (`7200` s becomes `"2h"`). Comments in a hand-written file are not preserved.
- **Exports.** JSON is the full result list. The summary CSV is a tidy table (replication, scope, id, name, metric, value); the event log CSV has one row per finished task. All times in exports are seconds.

## M3: collaboration

- **Instances of a case.** An arrival creates *all* instances of its triggers first and only then runs them, in trigger order. (Otherwise a case could look complete before a later pool's instance existed.) Processes without a trigger get an instance only when a message start event receives a message.
- **Active processes.** Binding follows message flows from the triggered processes (and from replying black boxes) to message start events and treats the receiving processes as part of the run: their tasks need `[activities]` entries and their elements are checked for support. Message start events, signal events and message events cannot be arrival triggers.
- **Messages** (§5.3). A message goes through the message flow within the sender's case and takes no time. At the target:
  1. a token is waiting at the target element: the longest-waiting one continues (`delivered`);
  2. the target is a message start event: a new instance is created in the case (`started_instance`); if the case is already complete the message is `lost`;
  3. otherwise it is stored if `[messages] buffer_unconsumed = true` (the default; `buffered`) or dropped (`lost`).
  A buffered message is taken by the next token that reaches that element in the same case. Buffered messages never picked up are reported as `undelivered`. Messages are matched per receiving *element*, not per message name.
- **Which elements send/receive.** Send tasks (after their duration), message throw events and message end events send; every message flow starting at them is used. Receive tasks, message catch events and message start events receive. A message flow from any other element, or to a pool that has a process, is a scenario error; the error says what to model instead (e.g. a send task with an incoming message flow: add a receive task or message catch event after it for the answer).
- **Message flows at call activities and subprocesses** (BPMN §9.3) only show on the outside what the elements inside send and receive, so the levels of a model stay consistent. They are allowed and never used: nothing is sent along them, black-box replies do not follow them, they do not start processes, and in the manual game they do not count as "sent by the model". The elements inside send and receive along their own message flows (for a call activity: those of the called file, within the child's message group). If the other end is an element of a modelled process, binding warns that it never gets (or sends) this message.
- **Receive task.** It only waits for the message: no resource, no duration, no `[activities]` entry.
- **Black boxes** (participants without a process). Messages to them are logged (`black_box`). With `[messages.black_box_reply] <participant> = <distribution>` they answer after the sampled delay along every message flow that leaves them; the reply is delivered like any message. Without a configured reply the receivers wait forever and show up as stuck.
- **Signals** (§5.4). Signal throw/end events broadcast by signal *name*. Only tokens waiting at a matching signal catch event at that moment receive it (all of them, in case/instance/token order); nothing is stored. `simulation.signal_scope = "global"` reaches all cases instead of the sender's. Every broadcast is logged with its receiver count, so missed signals are visible. Signal start events and signal boundary events come with M4.
- **Reports.** The result lists all messages with outcomes, the lost-message count, undelivered buffered messages and all signals; the GUI problems tab shows them.
- **Validation** now also warns about receive/catch message elements without an incoming message flow and send/throw message elements without an outgoing one.
- **Validation: levels that disagree.** For every call activity whose called process is loaded and every embedded subprocess that is a level of its own (drawn collapsed, i.e. with a shape on the file's first diagram but none of its content there, or with message flows at its border), validation compares the pools the inside exchanges messages with (per direction) with the message flows at the call activity or subprocess. A pool only the inside talks to ("show that pool and the message flow here too") and a message flow at the outside that nothing inside matches are warnings. Pools are matched by name (case and spacing ignored, else by id), since the same pool has a different id in every file.

## M4a: link/timer events, terminate, subprocesses, boundary events (single file)

- **Subscriptions.** A token that waits (catch event, receive task) or an activity with boundary events holds *subscriptions* to messages, signals or timers. Completing or cancelling the token deactivates them; a stale timer firing later does nothing.
- **Link events.** A link throw event moves its token immediately to the link catch event with the same name in the same process (V11); a catch event reached through a normal flow just passes. A throw without a matching catch is a binding error.
- **Timer catch events** need `[events.<id>] delay = <distribution>`. Message/signal catch events and receive tasks may also get an `[events]` entry (a trigger from outside the model): whichever happens first, message/signal or timer, continues the token.
- **Terminate end event.** At the top level of a process it cancels every other token of the instance (running tasks release their resource, queued requests are withdrawn, subscriptions end). Inside an embedded subprocess it cancels only the other tokens of that subprocess, which then completes normally. (Deviation from the spec's "ends the whole process instance" for the subprocess case; this is the BPMN definition.) Error and escalation end events behave like none end events (replaced in M9: thrown errors and escalations).
- **Cancelled tasks.** They are logged (`cancelled = true`) with the time they actually worked; the resource is released at once and charged only for that time (no fixed cost). Activity statistics report `runs` (completed) and `cancelled` separately; waiting/processing summaries cover completed runs only.
- **Embedded subprocess.** A token arriving at the subprocess starts a scope: one token at each none start event inside. The subprocess completes when its scope has no tokens left; the waiting token then leaves along the outgoing flow. It needs at least one none start event (M10: or no start event at all). Tokens created inside (AND/OR splits) stay in the scope.
- **Boundary events** (on tasks, receive tasks and embedded subprocesses) are armed when the token *arrives* at the activity, so time spent queueing for a resource counts towards a timer. Interrupting (`cancelActivity` true): the activity (task run or whole subprocess scope) is cancelled and the token continues on the boundary flow. Non-interrupting: an additional token starts on the boundary flow in the same scope; a timer fires once, message/signal boundaries stay armed.
  - **Timer:** `[boundary.<id>] delay = ...` (optional `probability`, default 1).
  - **Error / escalation:** `probability` and `delay`: with that probability the event fires `delay` after activation, if the activity is still active. (M9: on subprocesses and call activities thrown errors and escalations fire them too, and the entry is optional.)
  - **Message / signal:** no parameters. A message to a boundary event is never buffered: if its activity is not active, the message is lost.
- **Signal start events** create an instance in the sender's case for every broadcast of that name (recorded as `started` in the signal log). Processes with such a start event take part in the run when an active process throws the signal.
- **Not yet:** call activities (M4b), conditional/compensation/multiple event definitions, boundary events on call activities.

## M4b: call activities and several files

- **Discovery.** Opening a main file (`Project::open_main`, `sim-cli`, GUI "Open file…") loads that file plus, directly or indirectly, every `*.bpmn` in its folder that defines a process named by a call activity (`calledElement` or `zeebe:calledElement`) and every `*.dmn` that defines a decision named by a business rule task (`zeebe:calledDecision`). The folder is not searched recursively; unreadable unrelated files are ignored. If two files in the folder define a referenced process (or decision), opening fails naming both. References nothing defines are left to validation (warnings; see "Call activities without their process" below for processes). "Open folder…" loads every `.bpmn` and `.dmn` in it.
- **Qualified ids** (§3.2/§4) were already the basis of the model; scenario keys may be bare if unique across the loaded files, otherwise `"file.bpmn#id"`. `model.main` must name a loaded BPMN file and every entry of `model.files` must be loaded; neither changes which file arrivals use (triggers are resolved by id).
- **Call activity.** The called process is found globally by process id. Its none start events (top level) each get a token in a new *child instance* of the same case; the call activity completes when the child instance completes. Costs of the child belong to the case. Resource pools are global and matched by name, so parent and child compete for the same pool. Called processes must have a none start event (M10: or no start event at all); direct or indirect recursion is a binding error. A call activity can carry boundary events: an interrupting one cancels the child instance (and everything it called).
- **Message groups.** Messages are matched within a *group*: the top-level instances of a case form one group; every call activity starts a new group for the child instance and for whatever the child's messages start (message start events). This is how a called file's own collaboration (e.g. its black-box pool and message flows) applies to the child instance only, and how two calls of the same process in one case do not mix their messages. Signals still use the case (or all cases) as scope.
- **Instance statistics.** The result lists, per process, the number of completed instances and their cycle time (`processes`), excluding warm-up cases.
- **DMN.** Decision tables are not evaluated yet; found decisions are only shown (GUI model tree). The gateway after a business rule task still uses probabilities.
- **Unresolved calls** (§3.2): see "Call activities without their process" below.

## M5: calendars, horizon, replications, exports

- **Simulation clock.** Simulation time 0 is a real UTC date and time: `simulation.start`, default Monday 2024-01-01 00:00. It fixes the weekday calendars start on and the timestamps in exports (`YYYY-MM-DD`, `YYYY-MM-DDTHH:MM[:SS]` or with a space). Only resources have calendars; arrivals, timer events, boundary timers, black-box replies and horizons run on the wall clock.
- **Calendars** (`[calendars.<name>] days = [...], hours = "09:00-12:00,13:00-17:00"`, referenced by a resource's `calendar`). Other hours on other days are written as periods, each with its own days and hours: `periods = [{ days = ["mon", "tue", "wed", "thu", "fri"], hours = "20:00-24:00" }, { days = ["sat", "sun"], hours = "08:00-24:00" }]`; a single period is saved as `days` + `hours`. Intervals must not cross midnight or overlap on a day (also across periods); `24:00` is allowed as an end. A closing time itself counts as closed.
  - A task that gets its resource while the calendar is closed starts working at the next opening. The resource is claimed from the moment it is assigned; waiting time is start − arrival at the task.
  - A task still working at closing time pauses and continues at the next opening; its end time is wall-clock, its `work` (processing time) is working time only.
  - Costs and busy time use working time. Utilisation = busy time ÷ (count × calendar-open time within the observation window).
  - Cancelling a task (boundary event, terminate) counts the hours actually worked, including pauses.
- **Horizon.** `simulation.horizon` stops the run at that simulation time; events after it never happen. `cases` and `horizon` can be combined (whichever comes first); one of them is required. Tokens still alive at the horizon are reported as `unfinished` and are *not* counted as stuck (`stuck` is only used when the run ended because nothing more could happen, i.e. a deadlock). Work in progress at the horizon counts as busy time up to the horizon, and the observation window is the horizon.
- **Replications.** Seeds `seed`, `seed+1`, …. `aggregate()` reports, for the main figures, mean, sample standard deviation and the half width of a 95% confidence interval from Student's t (exact table up to 30 degrees of freedom, Cornish–Fisher expansion beyond). Quantities of elements that did not occur in a replication count as 0 for counts and costs; averages (waiting, cycle times) only use replications in which the element occurred. With one replication there is no interval.
- **Exports.** The event log CSV now has seconds and UTC timestamps, the working time and a `cancelled` flag. XES: one trace per replication and case (`<seed>-<case>`), a `start` and a `complete` event per task execution (`ate_abort` instead of `complete` for cancelled tasks, only the abort event if it never started), with `org:resource`. The aggregate CSV has n, mean, standard deviation and CI half width per metric.
- **CLI.** `sim-cli run` prints an aggregate block for more than one replication and writes `--json`, `--summary-csv`, `--aggregate-csv`, `--event-log` and `--xes`.

## M6: inclusive and event-based gateways

- **Inclusive (OR) split.** `[gateways.<id>] probabilities` gives each outgoing flow its own probability (0..1, no need to sum to 1); every flow is drawn independently, in model order. If none is chosen, the gateway's `default` flow is taken, otherwise the flow with the highest probability (the first one on ties). The default flow takes no probability (an entry for it is an error).
- **Inclusive (OR) join.** A token arriving at a join with several incoming flows waits there. Once all tokens of the instance have settled (after every step of the engine), a waiting join fires if no other token of the same instance *and the same subprocess activation* sits at an element from which the join can still be reached. Reachability is computed once per join: backwards over sequence flows, from link catch events to their link throw events, and from boundary events to their activity. When it fires it consumes one waiting token per incoming flow; extra tokens on the same flow wait for the next firing. Tokens waiting at another join count as "can still arrive", so two OR joins that each lie upstream of the other (OR joins in a loop) can wait for each other forever; this shows up as stuck tokens.
- **Event-based gateway.** The token waits at the gateway and subscribes to every following event: message catch events and receive tasks (messages), signal catch events (signals), timer catch events (`[events]` delay, which starts when the token reaches the gateway). Externally triggered `[events]` delays of message/signal targets are armed too. The first to happen moves the token on through that event; all other subscriptions are cancelled. A message already buffered for one of the targets is taken immediately. A message arriving after the gateway has decided is handled like any message for an element nobody waits at (buffered, then reported as undelivered, or lost). Each outgoing flow must lead to one of those events (binding error otherwise).

## M6: DMN decisions and gateway conditions

(Replaces "decision tables are not evaluated yet" from M4b.)

- **Decision tables.** Business rule tasks with `zeebe:calledDecision decisionId` whose decision is loaded are evaluated when the task completes (after its duration). Hit policies UNIQUE (default), FIRST, ANY and COLLECT (optionally SUM, COUNT, MIN, MAX); others (PRIORITY, RULE ORDER, OUTPUT ORDER) are binding errors. UNIQUE with several matching rules and ANY with differing outputs count as *violations* and use the first match. No matching rule gives null outputs (`no_match`). Required decisions (decision chaining), literal-expression decisions and input expressions other than variable names are not supported. A business rule task whose decision is not loaded only warns and runs as a plain task.
- **FEEL subset.** Input entries: `-`, literals (numbers, "strings", true, false, null), comparisons `<`, `<=`, `>`, `>=`, `=`, `!=` against a literal, ranges `[a..b]`, `(a..b)`, `]a..b[` (and mixed), comma lists (any test may match) and `not(...)`. Values of different types never compare (a test is then false, `!=` true). Output entries: a literal, or empty/`-` for null.
- **Variables.** Each process instance has its own variables (a called instance starts with none). A decision input is the instance variable of that name; if it does not exist yet it is sampled once from the scenario and stored, so later decisions in the same instance see the same value. Outputs are stored under their output names; with `resultVariable` also under that name (single output) or `<resultVariable>.<output>` (several outputs). COLLECT without aggregation stores a list.
- **Input distributions** (`[decisions."<id>".inputs]`): a number distribution (`{ dist = "uniform", min = 0.0, max = 100.0 }` etc., plain numbers without time units and *not* cut off at 0), a categorical choice (`{ choice = { gold = 0.25, silver = 0.75 } }`, must sum to 1) or a boolean (`{ p_true = 0.3 }`). A distribution given under any decision serves every decision that has an input of that name. Inputs that another decision produces need no distribution; every other input does (binding error).
- **Gateway conditions.** An XOR or inclusive split without a `[gateways]` entry, where every non-default outgoing flow has a `conditionExpression`, is decided by the conditions (FEEL, optional leading `=`): `name op literal` combined with `and`, `or`, `not(...)`, parentheses; names may be dotted; unknown variables are null; a comparison with a list holds if any element satisfies it. XOR takes the first true flow in model order, inclusive takes all true flows; if none holds, the default flow; without a default flow the token stays at the gateway and is reported as stuck ("no outgoing condition is true"; BPMN would raise an incident). JUEL (`${...}`) is a binding error. A `[gateways]` entry overrides the conditions (with a warning), so a model can still be run with probabilities.
- **Reports.** Per decision: evaluations, no-match count, violations and how often each output occurred (results, CLI, GUI).
- **Editing decision inputs (desktop app).** A business rule task's editor shows the decision by its name and description and each input under its DMN `label`, with variable name and type. The editor follows the type: text inputs as one of several values with a share each (values from `inputValues` and the rules can be added with one click, others typed in; values can be removed; a value no rule names is marked), yes/no inputs as "true in x % of the cases", numbers as a distribution with how often they fall below, between and above the numbers the rules compare with. The kind can only be changed when the type is not given or does not fit the scenario entry. An input another decision also reads says so (one value per case serves both). "What it gives" evaluates the decision for 2000 cases drawn from the inputs (fixed seed) and shows how often each output value comes out, how often no rule matches (null) and how often several rules match under UNIQUE or ANY. Inputs set by another decision are empty in this preview.

## Gateways that follow a decision output

(Extends "Gateway conditions" above to splits whose flows have no conditions, as in models that are not executable.)

- **Scenario.** `[gateways.<id>] output = "<variable>"` with `values = { <flow> = <value>, <flow> = [<value>, ...] }` decides an XOR or inclusive split by a variable a business rule task's decision sets: a flow is taken when the variable equals one of its values (strings, numbers, booleans). It is turned into the conditions `variable = value or ...`, so it behaves exactly like gateway conditions: XOR takes the first matching flow in model order, inclusive every matching flow; a list (COLLECT without aggregation) matches when it contains a value; if nothing matches, the default flow; without one the token stays at the gateway and is reported as stuck ("decision output <variable> = <value> takes no flow"). The variable is read when the token reaches the gateway, so it may be set by any decision evaluated earlier in the same process instance, also before joins (a decision with two outputs can decide two gateways). A called process does not see its caller's variables.
- **Several outputs.** A table with one output stores it under its output name and under the result variable; with several outputs under each output name and `<resultVariable>.<output>`. `output` names one of them; naming the result variable of a table with several outputs is a binding error that lists the parts.
- **Checks.** Binding errors: `output` not set by any loaded decision table of a business rule task; `values` without `output`; a non-default flow without values; the default flow with values (it is taken when nothing matches); a flow that does not leave the gateway; combined with `probabilities` or `if_completed`; on an element with conditional flows (only gateways). Warnings: a value no rule of the decision can give; a value the decision can give that no flow takes, when there is no default flow. Values computed by an aggregation (COLLECT with SUM etc.) are not checked.
- **Conditions in the model.** A split whose every non-default flow has a condition is still decided by its conditions without a `[gateways]` entry; an entry with `output` overrides them with a warning, like probabilities.
- **Skeleton and "Update from model".** A split without conditions gets an `output` entry instead of shares when the names of its non-default flows match the values of a decision output of its process: equal, or one containing the other, ignoring case, spaces and punctuation ("yes"/"no" also match true/false). Every non-default flow must match and no value may match two flows. Outputs of decisions evaluated closest before the split (walking back along incoming flows) are tried first. Otherwise the split gets equal shares as before.
- **Placeholder inputs.** Decision inputs get placeholders from their type (`typeRef` of the input expression) and allowed values (`inputValues`), else from what the rules compare them with, so that every rule can match: text values in equal shares (plus "other" when a rule tests `not(...)`), `p_true = 0.5` for booleans, and for numbers a uniform distribution around the compared numbers: half their range beyond the smallest and the largest, or the number's own size when only one is compared (at least 1), not below 0 unless a compared number is negative. Inputs no rule tests keep `uniform 0..100`.
- **Desktop app.** The editor of a split offers "Decide by: a decision output" when its process has a business rule task with a loaded decision table: the output (listed with the task that sets it) and, per non-default flow, the values the decision can give as toggles (typed in, comma-separated, when an aggregation computes them). The diagram badges show `variable = value` at the flows and "otherwise" at the default flow.
- **Manual game.** The player decides these gateways like any other.

## M6: diagram view

- **Layout.** The parser reads the shapes (`dc:Bounds`), edges (`di:waypoint`) and label positions (`bpmndi:BPMNLabel`) of the *first* `bpmndi:BPMNDiagram` of each file, keyed by qualified element id; lanes are kept with their ids. Further diagrams (e.g. the separate planes Camunda writes for collapsed subprocesses) are ignored, and malformed layout data is skipped instead of failing the load. The layout is only used for drawing.
- **Diagram tab** (GUI). One file at a time (files without BPMNDI are not offered). Pools and lanes with their names in a vertical header band (black-box pools, i.e. participants without a process, are plain boxes with the name in the middle), sequence flows (solid, filled arrow) and message flows (dashed, circle at the start, open arrow), events with their marker (message, timer, signal, link, error, escalation, terminate; filled markers for throwing events; double ring for intermediate and boundary events, dashed for non-interrupting ones; thick ring for end events), gateways (×, +, ○, event-based), tasks with their type marker in the top-left corner (user, service, script, manual, business rule, send = filled envelope, receive = open envelope), call activities (thick border and the collapsed "+" marker) and expanded subprocesses (outline). All markers are drawn as vector shapes, not font glyphs. Boundary events are drawn on top of their activity. Navigation: drag, or swipe with two fingers on a touchpad (mouse wheel: up/down, Shift + wheel: sideways), to move the view; pinch (or Ctrl/Cmd + wheel) to zoom around the pointer; "Fit" to show everything. Names of sequence and message flows are drawn at their label position, or next to the middle of the flow if the file gives none; names of events and gateways likewise at their label position, else below the element. Hovering an element shows its statistics.
- **Flow markers.** A default flow (the `default` of a gateway or activity) gets a slash across its start; a conditional flow leaving an activity or event gets a small diamond at its start (conditions after gateways are not marked, as in BPMN).
- **Artifacts** are drawn but never simulated: data stores (cylinder), data object references (sheet with a folded corner), text annotations (bracket with the text) and groups (dashed box with the name); associations as dotted lines, data input/output associations (and directed associations) with an open arrow head.
- **Opening called processes.** Clicking a call activity opens the diagram of the file that defines the called process (the pointer turns into a hand and the tooltip says which). "◀ <file>" goes back along the way you came; choosing a file in the list starts afresh. A called process without BPMNDI only shows a status message.
- **Heat map** (needs a run; uses the replication selected on the Results tab): mean waiting time, mean processing time or completed runs per activity, or the utilisation of the resource pool an activity used (taken from the event log); with utilisation, lanes and pools named like a resource pool are tinted too. Colours go from green (0) to red (the largest value shown).
- **Token replay.** Playback runs in real time at a chosen speed (simulated time per real second: automatic, which shows a typical task for about 1.5 s, or 1 min/s up to 30 days/s), with Play/Pause, Restart, Next event, a time slider and a clock showing the real date (`simulation.start`). Two modes:
  - *Follow cases* (default): one or up to 20 consecutive cases, each in its own colour; the clock is limited to the time between the first case's arrival and the last one's completion, and playback stops there. Tokens are drawn where they are: travelling along a sequence flow, waiting in front of a task (queued for its resource), being worked on inside it, or waiting at an event or gateway; messages travel as envelopes along their message flow. Moving between elements takes no simulated time, so a token is shown travelling for 0.6 s of screen time after it arrived (it reaches its target slightly "late" on screen). Tokens inside called processes appear when that file's diagram is open.
  - *All cases (queues)*: an orange bar in front of each task, growing with the number of executions waiting for a resource (full height at 10), and a blue badge with the number being worked on.
- **Token trace.** Following cases needs the token trace, which the engine records for the first `simulation.trace_cases` cases (default 100; 0 switches it off): every arrival of a token at an element, with the sequence flow it came over, and when a token is consumed (end event, merged at a join, cancelled). Recording it does not change any result. Cases beyond the limit fall back to the queue view.

## Manual simulation (token game)

`sim_core::manual::Game`, the "manual simulation" switch in the Diagram tab. One case is played by hand, without time, durations or resources; scenario parameters are not used.

- **Starting.** Tokens start at the none/timer start events of the loaded processes (button or click on the highlighted start event). Several pools can be started, all in the same case. Processes that a call activity calls are not offered: they start through the call.
- **Tasks** wait for the player: a click on the task (or its button) completes it and the token moves on. Switching "stop at tasks" off lets tokens run through tasks by themselves.
- **Events** wait for the player too (switch "stop at events" off to let them pass): every intermediate throw event (also plain ones and link throw events, before they jump) and every link catch event; a message / signal / error / escalation / terminate end event stop *before* they send ("Send from …"); a message or signal catch event stops once its message or signal has arrived, and a message- or signal-started start event stops where it was triggered ("Go on from …"); a receive task whose message arrived stops like any task. Events whose message the model itself sends are not fired by hand: they wait until that message is sent.
- **Automatic steps.** Everything else that needs no decision happens at once: AND splits and joins, inclusive joins (same rule as the engine: fire when no token can still arrive), throw and end events, messages (delivered within the message group as in the engine: to a waiting receiver, starting an instance at a message start event, or kept until the receiver waits), signals (to every waiting signal catch event, signal start events), links, terminate, embedded subprocesses and call activities (the child runs in its own file's diagram and the call continues when it completes).
- **Decisions by the player.** XOR splits (exactly one outgoing flow) and inclusive splits (one or more: tick the flows, then Go) — click the highlighted flow in the diagram or use the buttons; gateway conditions and probabilities are ignored. Event-based gateways: the player picks which following event happens, unless a message for one of them is already there (then it wins at once) or the model sends one later. Catch events and receive tasks: timers, signals and messages that no modelled element sends (messages from black boxes or from nowhere) are fired by the player; messages sent by the model are waited for. Boundary events of the activity a token is at (a task when stopping at tasks, an embedded subprocess, a call activity) can be fired too; interrupting ones cancel the activity.
- **Following the case across files.** After every step the diagram shows the file of the token that just came to rest and waits for the player: when a token enters a call activity the called process's diagram opens; when the called process ends and the case continues in the caller, the caller's diagram is shown again. "Back" leads along the chain of calling files. If the case runs on by itself from one called process into another (e.g. A ends and the caller immediately calls B), the view goes straight to B.
- **Undo / Reset / Log.** Every action can be undone; Reset starts a new case; the log lists what happened in words.

## M9: conditional flows leaving activities

(Replaces "a node with several outgoing flows sends a token down each of them" from M1 for activities and events with conditional flows.)

- **Which elements.** An activity or event (not a gateway) with at least one outgoing flow that has a `conditionExpression`. A `default` flow on an element without conditional flows is an ordinary flow.
- **Routing** when the element is left (after the task's duration and its decision, after the subprocess or call completes, when the event fires): every outgoing flow without a condition is taken, plus every conditional flow whose condition holds; if no condition holds, the default flow is taken. Flows are taken in model order. If no condition holds and there is neither a default flow nor an unconditional flow, the token stays at the element and is reported as stuck ("no outgoing condition is true"), as at gateways.
- **Conditions** are the same FEEL subset as gateway conditions and read the instance's variables; JUEL is a binding error.
- **Probabilities instead.** A `[gateways.<element>] probabilities` entry gives each *conditional* flow its own probability (drawn independently, like an inclusive split) and replaces the conditions. Unconditional and default flows take no probability (an entry for them is an error).
- **Manual game.** The player ticks which conditional flows hold (or the default flow) and presses Go; the unconditional flows go along. Choosing nothing is not possible, so "no condition holds" means choosing the default flow.

## M9: thrown errors and escalations

(Replaces "error and escalation end events behave like none end events" from M4a.)

- **Codes.** `bpmn:error` and `bpmn:escalation` elements are read with their `errorCode` / `escalationCode` (else their name, else their id). Events refer to them by `errorRef` / `escalationRef`, and matching is by code, so a called process in another file can declare its own error element with the same code. An event without a ref has no code.
- **Throwing.** Error end events throw an error; escalation end events and escalation intermediate throw events throw an escalation (after their messages and signals, if any).
- **Catching.** The catching activity is the closest enclosing embedded subprocess or call activity, innermost first (from a called process's top level the search continues at the call activity in the calling instance), that has a matching boundary event. At one activity a boundary event with exactly this code wins over a catch-all boundary event without a code. Boundary events on the thrower's own task cannot catch: a task throws nothing.
  - An error is always interrupting: the activity is cancelled with everything inside it (tasks release their resources, called instances are cancelled) and its token continues on the boundary flow.
  - An escalation caught by an interrupting boundary event does the same; by a non-interrupting one, an extra token starts on the boundary flow and the thrower goes on.
  - Each catch counts in `boundary_fired`.
- **Uncaught.** An uncaught error leaves its token at the end event, reported as stuck with the state `uncaught error '<code>'` (Camunda raises an incident). An uncaught escalation has no effect.
- **Probabilities as well.** On tasks, error and escalation boundary events still need a `[boundary]` entry (`probability`, `delay`): nothing in the model throws there, so they stand for failures the model does not show. On subprocesses and call activities the entry is optional and adds such failures on top of thrown errors; whichever comes first wins. The skeleton only writes entries for those on tasks.
- **Manual game.** The same rules; the log says which boundary event caught the error or escalation, or that an error was not caught (its token stays at the end event).

## M9: multi-instance activities and loops

- **Model.** `multiInstanceLoopCharacteristics` (`isSequential`, `loopCardinality`, `completionCondition`, `zeebe:loopCharacteristics inputCollection`) and `standardLoopCharacteristics` (`testBefore`, `loopMaximum`, `loopCondition`) are read for tasks, embedded subprocesses and call activities.
- **Number of instances**, first that applies:
  1. `[multi_instance.<id>] count = 3`, or a distribution of plain numbers: `count = { dist = "uniform", min = 1, max = 5 }` draws whole numbers from 1 to 5 with equal chances; other distributions are rounded to the nearest whole number (at least 0).
  2. `loopCardinality` if it is a whole number (`5` or `= 5`).
  3. `inputCollection` (or `loopCardinality`) if it is a variable name that a decision sets: the length of the list (a COLLECT result), or the number. Anything else counts as 0 instances.
  Otherwise binding fails. `completionCondition` is ignored with a warning: all instances run.
- **Execution.** The token waits at the activity while its instances run, each as a token of its own that runs the activity once (a task with its own duration, resource and cost; a subprocess scope; a called instance). Parallel instances start together and compete for resources; sequential ones start one after the other. The token leaves along the outgoing flows when the last instance is done; with 0 instances it passes straight through. Activity statistics count every instance as a run. Process variables are shared; there is no per-instance `inputElement`.
- **Standard loop.** `[loops.<id>] repeat_probability = p` is required (`loopCondition` is not evaluated): after each iteration the activity runs again with probability p, at most `loopMaximum` times. With `testBefore="true"` the first iteration is decided the same way, so the activity may not run at all. p = 1 without `loopMaximum` is a binding error.
- **Boundary events** of a multi-instance or loop activity are armed once, for the activity as a whole. An interrupting one cancels every running and queued instance; an error thrown inside one instance of a subprocess is caught by the activity's boundary event and cancels all of them.
- **Skeleton.** Multi-instance activities without a whole-number cardinality or a decided collection get `count = 3`; loop activities get `repeat_probability = 0.2`.
- **Manual game.** A multi-instance or loop activity is played once; the log says so.
- **Diagram.** Three vertical bars (parallel), three horizontal bars (sequential) or a circular arrow (loop) at the bottom of the activity.
- **Event log.** Activity records carry the token that ran them, so the replay shows each instance of a parallel task in its own state.

## M10: BPMN 2.0.2 conformance

Checked against the execution semantics of BPMN 2.0.2 (clause 13). The simulator is *based on* BPMN 2.0.2 but does not claim Process Execution Conformance (§2.1, §2.3): conditions, timers and data are partly replaced by scenario parameters, and some elements are not run (see M0).

- **No start event** (§10.5.2, §13.3.4). An embedded subprocess or a called process without any start event starts with one token at every activity and gateway without incoming sequence flows (event subprocesses excluded), in the engine and in the token game. Such a level may also leave out end events: its elements get no "no incoming/outgoing sequence flow" warning. A level that has start events but no none start event is still an error. Top-level processes are still started only by their start events.
- **Reported, not run.** Receive tasks with `instantiate="true"` and event-based gateways that start a process (`instantiate="true"`, or no incoming flow unless it starts a level without start event) are validation warnings: they are never reached, only start events start a process.
- **Event subprocesses** (`triggeredByEvent`, §10.3.5, §13.5.4) at the top level of a process or inside an embedded subprocess (also inside another event subprocess). Its one start event has a message, signal, timer, error or escalation trigger and `isInterrupting` (default true; error ones are always interrupting); event subprocesses have no sequence flows and no boundary events. Other shapes are binding errors.
  - *Listening.* While its scope runs (the top level of an instance, or one activation of the subprocess, i.e. one instance of a multi-instance subprocess), the start event waits for its message (within the message group, never buffered: a message arriving while the scope does not run is lost) or signal, or for its `[events.<start event>] delay` (required for timers; for message and signal starts an optional trigger from outside the model, as at catch events). Errors and escalations need no entry: the search for a catching handler (M9) looks at the event subprocesses of a scope before the boundary events of the activity around it, exact codes winning over catch-alls; what an event subprocess throws goes past the event subprocesses next to it.
  - *Running.* The event subprocess runs as its own scope, with a token waiting at it in the enclosing scope, so the scope (and the instance) completes only after it. Interrupting: everything else in the scope is cancelled first (tasks release their resources, called instances are cancelled) and no other event subprocess of that scope starts any more. Non-interrupting: it runs next to the rest; message and signal starts stay armed (several can run at once), a timer fires once. Once only event subprocesses are left in a scope, it starts no new ones.
  - Each start counts in `boundary_fired` (results, GUI). Arrival triggers must be top-level start events; a trigger inside a subprocess (as earlier skeletons wrote for embedded subprocesses) is ignored with a warning. The skeleton writes `[events]` entries for timer starts of event subprocesses.
  - *Manual game.* An event subprocess can be started by the player while its scope runs (offered at the token of its subprocess, or at a top-level token for the top level): timers, signals and messages the model does not send. Messages and signals the model sends, errors and escalations start them by themselves. The log says which event subprocess started and whether it interrupted.
  - *Diagram.* Event subprocesses have a dotted outline; non-interrupting start events a dashed ring.
- **Deviations kept on purpose:**
  - *Inclusive join.* The join waits while any token of the instance (and subprocess activation) can still reach it (M6). §13.4.3 only lets a token block the join if it can reach an incoming flow without a token and no incoming flow with one, so the spec may fire the join earlier and then once more for the late token. The engine's rule is the one modellers expect and the one Camunda uses.
  - *Signal scope.* Signals reach only the sender's case by default (M3); §10.5.1 broadcasts them across processes and pools, which `simulation.signal_scope = "global"` does. In a simulation of many concurrent cases the case scope is usually what the model means.
  - *Terminate inside a subprocess.* The subprocess ends and its token leaves along the outgoing flows (M4a). §13.5.6 calls this "abnormally terminated" without saying what happens next; Camunda continues the same way.

## Configuring in the desktop app

- **What an element needs.** `sim_core::needs` decides which elements take parameters: tasks a duration (receive tasks none; call activities whose process is not loaded too), XOR and inclusive splits probabilities or a decision output (unless every non-default flow has a condition), timer catch events and timer starts of event subprocesses a delay, timer boundary events a delay, error and escalation boundary events on tasks a probability and a delay, multi-instance activities a count (unless the model or a decision gives it), standard loops a repeat probability, business rule tasks distributions for the decision inputs no other decision sets. Top-level none and timer start events can be arrival triggers. The skeleton, "Update from model" and the GUI all use this list.
- **Update from model.** Adds placeholder entries (with qualified ids) for elements the scenario does not cover, the resource pools tasks use, and an arrival if there is none. Existing entries are never changed. Entries whose element no longer exists are listed and removed only on request. It runs by itself when a model is opened while a scenario is loaded, and when a scenario file is loaded.
- **Still to check.** The GUI remembers which values are placeholders (generated by the skeleton, an update, or a click on an unconfigured element) and marks them: a dashed amber outline in the diagram, an amber dot in the scenario tab. Editing a value, or "Done" in the diagram editor, marks it checked. Elements with errors are outlined red. A loaded scenario counts as checked. This state is not saved in the scenario file.
- **Configure mode.** In the diagram, configure mode shows the parameters as badges (durations as the mean, "~" for random ones; split shares at the flows; arrivals at start events; resources, cost, calendar and pilot load at lanes) and opens an editor next to an element, lane or pool header when clicked. The editor of a resource pool picks its working hours from the calendars of the scenario or makes a new one (Mon–Fri 09:00–17:00, named "office", "office 2", …) and edits its days and hours in place, with further periods for other hours on other days; a calendar can be shared by several pools, and the editor says which others use it. "Next" goes through what still needs input in reading order, across files. Errors are reported with the element (or resource pool) they are about, so the problem lists of the scenario and run tabs jump to it.
- **XOR shares** are edited so they add up to 100 %: the last flow takes the rest, and the dividers of the bar move the share between neighbouring flows. A scenario whose shares do not add up still shows them and offers to scale them.
- **Distribution preview.** 2000 samples drawn as the simulation draws them (cut off at 0, fixed seed): a histogram between the 1st and 99th percentile with the mean, and the 10th to 90th percentile as "usually ... to ...". Arrival rates are shown per hour, day or week from the mean time between cases.
- **Quick check (pilot run).** 0.4 s after the last change the scenario is run in the background as one replication of at most 300 cases (no warm-up, no horizon, every case traced). It shows the cycle time and, per resource pool, the load: the work done by the pool divided by its capacity (resources times open time of its calendar) between the first and the last arrival. Above 100 % the pool cannot keep up and the queue keeps growing, which the utilisation of a finite run does not show (it stays below 100 % because the run stretches). Flows are drawn wider the more tokens passed them. The quick check can be switched off.

## Pools that coordinate within a case

For collaborations whose pools start together (one arrival triggering a start event in each pool) and ask each other about progress: "is the part ready yet? If not, ask for it and wait."

- **Gateways that ask the case's history.** An XOR split with two outgoing flows can be decided by what has happened in its case instead of by shares: `[gateways.<id>] if_completed = "<element>"`, `then = "<flow>"`. When a token reaches the gateway, it takes `then` if that element has completed in the same case, otherwise the other flow. "Completed" means: a task or call activity finished (not cancelled; a multi-instance activity once all its instances are done), an event was passed or an end event reached, a subprocess completed. A throwing event or a send task counts as completed *before* its signals and messages go out, so a receiver that checks right away already sees it. The history covers every instance of the case (all pools, called processes, message-started instances) and only that case, also with `signal_scope = "global"`. `probabilities` and `if_completed` cannot be combined. Inclusive splits, splits with more than two flows and conditional flows leaving activities cannot ask the history (binding error).
  - *Why.* Shares decide such a question at random: a pool may "find" a result that does not exist yet, or decide "not yet" after the signal announcing the result has already been broadcast and then wait for it forever (signals are not stored). Asking the history keeps the check and the wait consistent: the gateway says "not yet" exactly when the signal is still to come.
  - *Desktop app.* The editor of a two-way XOR split offers "Decide by: shares / what happened in the case", with the element to ask about (any non-gateway element, listed by pool) and the flow to take once it has completed. The diagram badges show "once <element> done" and "until then" at the flows.
  - *Manual game.* The player decides these gateways like any other.
- **Starting later than the case.** A top-level timer start event that an arrival fires may have `[events.<id>] delay = <distribution>`: its instance is created with the case but its token waits at the start event for the sampled delay (shown as waiting in the replay). Without an entry it starts at once, as before. Other pools of the case are not affected, so each pool can begin at its own time after a common date (e.g. the first of a month). The instance's cycle time counts from its first token's start. An entry for a timer start event that no arrival fires is reported as a warning and not used. In the desktop app, the arrival editor of a timer start event offers "starts later than the case"; the badge shows "starts after ...".
- **Call activities without their process** (§3.2). A call activity whose called process is not in any loaded file is a validation *warning*. With an `[activities]` entry (duration, optional resource, fixed cost) it runs like a task: it uses the resource pool of its lane or pool, is logged and reported like a task, and its boundary events work as on tasks. Without an entry, binding fails and says so. If the called process is loaded, it is called and the entry is ignored with a warning. The skeleton, "Update from model" and the configure view give such call activities a duration.
